# FHGFF3: FAIR header for GFF3 annotations

**Status: v0.1 (document status; the schema contract is `schemaVersion` `"1.0"`), first
released in FAIR-bioHeaders-Specification v0.4.0.** FHGFF3 is the working name (#54), and the
fields may still change after curator review, through a new schema version. Its persistent
schema URL is `https://w3id.org/fair-bioheaders/fhgff3/v0.4.0`. The design is in
[specs/007-gff3-header](../specs/007-gff3-header/spec.md).

FHGFF3 is a provenance header around ordinary GFF3. It adds YAML lines that start with `#~` after
`##gff-version 3`, and one SHA-512/256 checksum over the file's exact bytes. It records which
genome the annotation's coordinates refer to and how the annotation was made.
- A header never makes the features valid.
- A GFF3 file without a header is still plain, valid GFF3.
- Feature validation is the job of the [gff3-validator](https://github.com/FAIR-bioHeaders/gff3-validator),
  which reports header results and feature results separately.

FHGFF3 was written fresh in this repository. No file comes from the FHGFF3 fork of
biodatamodels/gff-schema, whose upstream licence is unresolved (#75).

## Where the header goes

```
##gff-version 3
#!genome-build Synthetic SyntheticAssembly1
#~schema: https://w3id.org/fair-bioheaders/fhgff3/v0.4.0
#~schemaVersion: '1.0'
#~annotation: Synthetic example annotation
##sequence-region ctg1 1 20
#~# more fields
#~checksum: …
ctg1	synthetic	gene	1	20	.	+	.	ID=gene1
```

- Line 1 is `##gff-version 3` (or `3.x.y`), as GFF3 requires.
- The header block runs from line 2 to the first line that is neither blank nor starts with `#`
  (the first feature, or a `>` line), or to the `##FASTA` line, whichever comes first.
- Inside it, `#~` lines can be mixed with native directives (`##sequence-region`, `##species`,
  `##genome-build`, `###`), `#!` lines and comments, in any order.
- A `#~` line on line 1, after a feature, after `##FASTA` or in the FASTA section makes the file
  invalid.

The checksum covers every byte of the file, including native directives, the features, any
`##FASTA` section and any parent checksums in the header. Only the root `#~checksum:` line is
excluded. Tools that sort or tidy GFF3 (for example `gt gff3 -sort -tidy`) change bytes, so their
output's copied header no longer verifies. Validation reports that; nothing repairs it.

## Fields

Required are the core's required fields (`schema`, `schemaVersion`, `taxon`, `version`,
`metadataAuthor`, `dateCreated`, `checksum`), plus:

| Field | Value |
| --- | --- |
| `annotation` | Name of the annotation |
| the genome link | At least one of the two forms below |

`schema` must be an FHGFF3 schema URL ([SCHEMA-VERSIONS.md](SCHEMA-VERSIONS.md)): preferably the
versioned `https://w3id.org/fair-bioheaders/fhgff3/v0.4.0` of the release a file targets, or the raw
GitHub URL of `fhgff3.json` on `main` or at a release tag, under either repository name. `schemaVersion` is `'1.0'` (FHGFF3 1.0),
quoted in YAML.

### The genome link

The genome is the one assembly the coordinates refer to.

- **By FHR checksum** (verifiable): a `derivedFrom` item with `headerType: FHR`,
  `relationship: annotates` and the genome file's FHR checksum.
- **By accession and SeqCol digest** (asserted): `genomeReference` with `accession` (with its
  version, as published), `seqcol_id` (the GA4GH sequence collection digest you supplied), and
  optionally `assemblyName`. Use it when the genome has no FHR header, for example a public
  `GCF_`/`GCA_` FASTA.

Both forms may be given for the same genome. The checksum is then authoritative. At most one
`derivedFrom` item may have the relationship `annotates`, and it must name an FHR parent. Further
parents (for example the source annotation of a liftover) can be listed in `derivedFrom` with
other relationships.

### Optional fields

Leave a field out when you do not know its value. Tools never infer these values from the
features.

| Field | Value |
| --- | --- |
| `source` | Sources that are not FAIR-bioHeaders files, such as an annotation release or an evidence set: `name` (required), `release`, `setIdentifier`, `url`, `assemblyAccession`, `sequenceCount`, `description` (the same object as FHP's) |
| `annotationSoftware` | List of `{name, version, uri, commandLineOption}` |
| `annotationProtocol` | URI of the annotation protocol or workflow |
| `soVersion` | The Sequence Ontology release used for the feature types, as its `data-version` (for example `2026-08-07`) |
| `featureCounts` | List of `{featureType, count}`. `featureType` is the column-3 type as written (`gene`, `mRNA`, `SO:0000704`) |
| `completeness` | BUSCO counts, as in FHP |

The optional core fields (`voucherSpecimen`, `accessionID`, `scholarlyArticle`, `documentation`,
`identifier`, `relatedLink`, `funding`, `reuseConditions`) mean the same as in FHR. Genome-only
FHR fields (`genome`, `assemblyAuthor`, `masking`, `vitalStats`, `assemblySoftware` and the
others) and FHP-only fields are not FHGFF3 fields. Every object rejects unknown keys and `null`.
There is no required "method" field: describe how the annotation was made with the software,
protocol and `source` values.

### Native directives

The header does not replace GFF3's own directives. Where both describe the same thing, tools
compare them and **warn** about a disagreement. They never rewrite either, and a disagreement does
not make the file invalid.

| Header value | Native line | Comparison |
| --- | --- | --- |
| `taxon.uri` | `##species` | The numeric NCBI Taxonomy ID, whatever the URL form (`identifiers.org/taxonomy:9606`, NCBI's `wwwtax.cgi?id=9606`) |
| `genomeReference.accession`, or the `annotates` item's `accessionID.name` | `#!genome-build-accession` | Exact, version included; a `NCBI_Assembly:`-style prefix is ignored |
| `genomeReference.assemblyName` | `##genome-build`, `#!genome-build` | Exact, against the build name (the last word of the line) |

A value missing on either side is not compared.

### Assertions and checks

Every provenance value is the producer's statement. `bioheaders verify-links` reports, for each
recorded parent, `matched`, `not matched` or `not checked`:
- The checksum genome link is checked against a supplied genome file.
- `genomeReference` can be matched only against a supplied FHR genome whose own header records the
  same SeqCol digest. The tools never compute SeqCol digests.

A match establishes identity, not that the annotation is correct.

## Rules

FHGFF3 files follow the shared header and checksum rules R1 to R9 and R12 of [FORMAT.md](FORMAT.md)
unchanged, and R10 with the GFF3 block end below. In addition:

- [G1] Line 1 is `##gff-version 3`. The leading header block runs from line 2 to the first
  nonblank line that is not a `#` line, or to the `##FASTA` line. `#~` lines may be mixed with
  other `#` lines inside it. A `#~` line on line 1 or after the block is invalid.
- [G2] FHGFF3 metadata must validate against `fhgff3.json`. That includes the genome link: an
  `annotates` link to an FHR genome, a complete `genomeReference`, or both.
- [G3] A record is read as FHGFF3 only when its `schema` is an FHGFF3 schema URL: the raw-main or
  raw tag URL of `fhgff3.json`, or `https://w3id.org/fair-bioheaders/fhgff3/vX.Y.Z`; which FHGFF3
  schema is used follows [SCHEMA-VERSIONS.md](SCHEMA-VERSIONS.md). Tools validate
  any other header as that type (FHR by default), so a GFF3 file that cites `fhr.json` is checked
  against FHR.

The bracketed ids are stable labels used by the [conformance vectors](../conformance/README.md).
They add no requirements.

## Examples

All genome identifiers in the examples are placeholders (`SYNTHETIC_ASSEMBLY.1`, a SeqCol digest
of `S` characters), except the checksum of the synthetic genome `genome.fhr.fasta`, which the
checksum-linked examples cite.

| File | Shows |
| --- | --- |
| `genome.fhr.fasta` | The synthetic FHR genome the annotation refers to |
| `annotation.fhgff3.gff3`, `annotation.fhgff3.yaml` | A checksum genome link; the metadata and the headed file |
| `minimal-reference.fhgff3.json` | An accession-plus-SeqCol genome link |
| `rich.fhgff3.yaml` | Both links, software, SO release, counts and a source |
| `embedded-fasta.fhgff3.gff3` | A `##FASTA` section covered by the checksum |
| `no-header.gff3` | Plain GFF3: valid, with no header findings |
| `header-invalid.fhgff3.gff3` | A header with no genome link (fails G2) |
| `stale-parent.fhgff3.gff3` | A header whose genome checksum names an older genome: valid on its own, `not matched` against `genome.fhr.fasta` |

## Not yet available

These remain follow-ups in the [plan](../specs/007-gff3-header/plan.md):

- JSON-LD and HTML microdata forms (F-01).
- Header checks in the gff3-validator's browser build (F-04).

F-02 (the persistent schema alias, with the release) is complete: v0.4.0 is tagged, and
`https://w3id.org/fair-bioheaders/fhgff3/vX.Y.Z` selects that release's `fhgff3.json`
(registered in perma-id/w3id.org#6890).

FHGFF3 v0.1 was released from the `release-v0.4` line with FAIR-bioHeaders-Specification
v0.4.0, as FHP was (FAIR-bioHeaders-Specification#97). Its persistent schema URL is
`https://w3id.org/fair-bioheaders/fhgff3/vX.Y.Z`, the FAIR-bioHeaders-Specification release
tag, and it serves the v0.4.0 release. `fhgff3.json` on `main` is generated from the same
v0.4 core, not the core's v0.3 patterns.
