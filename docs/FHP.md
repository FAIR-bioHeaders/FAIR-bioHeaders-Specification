# FHP: FAIR header for protein FASTA

**Status: v0.1 (document status; the schema contract is `schemaVersion` `"1.1"`, released in
FAIR-bioHeaders-Specification v0.5.0; `"1.0"` was first released in v0.4.0).** FHP is the working name (#54), and the
fields may still change after curator review, through a new schema version. Its persistent
schema URL is `https://w3id.org/fair-bioheaders/fhp/v0.5.0` (v0.4.0 for FHP 1.0). The design is in
[specs/006-protein-header](../specs/006-protein-header/spec.md).

FHP brings the FHR header to protein FASTA files: predicted proteomes, sets taken from protein
databases, and curated sets that combine both. It works the same way as FHR:
- YAML lines that start with `;~` at the top of the file;
- one SHA-512/256 checksum over the file's exact bytes;
- a small required set, with everything else optional.

An FHP header records **asserted provenance**. It is not a quality-control report.

## Fields

Required are the core's required fields (`schema`, `schemaVersion`, `taxon`, `version`,
`metadataAuthor`, `dateCreated`, `checksum`), plus:

| Field | Value |
| --- | --- |
| `proteome` | Name of the protein set |
| `sourceType` | `predicted`, `database` or `mixed` (see below) |

`schema` must be an FHP schema URL ([SCHEMA-VERSIONS.md](SCHEMA-VERSIONS.md)): preferably the
versioned `https://w3id.org/fair-bioheaders/fhp/v0.5.0` of the release a file targets, or the raw
GitHub URL of `fhp.json` on `main` or at a release tag, under either repository name. `schemaVersion` is `'1.1'` (FHP 1.1; `'1.0'` with the v0.4.x schemas), quoted
in YAML.

The following fields are optional. Leave a field out when you do not know its value; tools never
infer these values from the sequences.

| Field | Value |
| --- | --- |
| `derivedFrom` | Parent FAIR-bioHeaders files by checksum (the core structure): `headerType` (`FHR`, `FHT`, `FHP`, `FHGFF3`), `checksum`, `relationship` (for example `translatedFrom`, `filteredFrom`), optional `seqcol_id` and `accessionID` |
| `source` | Sources that are not FAIR-bioHeaders files: `name` (required), `release`, `setIdentifier`, `url`, `assemblyAccession` (as the source states it), `sequenceCount`, `description` |
| `geneticCode` | NCBI translation table ID: 1–6, 9–16 or 21–33. Leave it out when the file mixes tables (for example nuclear and mitochondrial proteins) |
| `isoformPolicy` | `all`, `longestPerGene`, or `canonicalPerGene` (the source's canonical choice, which is not necessarily the longest) |
| `predictionSoftware` | List of `{name, version, uri, commandLineOption}`, with the same shape as FHR's `assemblySoftware` objects |
| `predictionProtocol` | URI of the prediction or annotation protocol |
| `sequenceStats` | `sequenceCount`, `geneCount`, `totalResidues` |
| `completeness` | BUSCO counts: `lineageDataset` with its version suffix (for example `primates_odb10`), `completeSingle`, `completeDuplicated`, `fragmented`, `missing`, `total`, and optional `buscoVersion` and `mode` |

The optional core fields (`voucherSpecimen`, `accessionID`, `scholarlyArticle`, `documentation`,
`identifier`, `relatedLink`, `funding`, `reuseConditions`) mean the same as in FHR. Genome-only
FHR fields (`genome`, `assemblyAuthor`, `masking`, `vitalStats`, `assemblySoftware` and the
others) are not FHP fields. Every object rejects unknown keys and `null`, except that from FHP 1.1
the top level accepts extension fields, keys that start with `x-` ([FORMAT.md](FORMAT.md) R15).

Quote release names such as `'2026_03'` in YAML. Unquoted, YAML 1.1 reads `2026_03` as the
number 202603.

### sourceType

`sourceType` says where the sequences came from. It does not say whether they were reviewed:
UniProt records review status per sequence (`sp` or `tr` in each FASTA header).

- `predicted`: every sequence was produced by a gene-prediction or annotation run (translated
  gene models or ORFs).
- `database`: every sequence was taken from a published database release, set or annotation run,
  for example a UniProt proteome, an Ensembl `pep.all` file or an NCBI annotation's proteins.
- `mixed`: the set combines more than one origin, or adds sequences contributed in other ways,
  such as manual corrections. List each origin in `source` and/or `derivedFrom`; no single entry
  needs to cover the whole set.

### Assertions and checks

Every provenance value is the producer's statement. Tools that check something report what they
checked, separately, and never write the result into the header.

`bioheaders verify-links` compares the recorded parent checksums with parent files on disk and
reports, for each parent, `matched`, `not matched` or `not checked`. A match establishes file
identity, not that the translations are correct. A `source` entry, and an `assemblyAccession`
stated by a source, cannot be verified this way.

## Rules

FHP files follow the shared header, checksum, number and link rules R1 to R15 of [FORMAT.md](FORMAT.md)
unchanged, in a FASTA container. The sequence alphabet makes no difference to them: stop symbols
(`*`), the rare residues U and O, the ambiguity codes B, Z, J and X, lower case and gaps are
ordinary bytes, hashed and preserved exactly. In addition:

- [P1] FHP metadata must validate against `fhp.json`.
- [P2] A record is read as FHP only when its `schema` is an FHP schema URL: the raw-main or raw
  tag URL of `fhp.json`, or `https://w3id.org/fair-bioheaders/fhp/vX.Y.Z`. Which FHP schema is used
  follows [SCHEMA-VERSIONS.md](SCHEMA-VERSIONS.md). Tools validate any other FASTA or GFA header as
  FHR, so a protein file that cites `fhr.json` is checked against FHR.

The bracketed ids are stable labels used by the [conformance vectors](../conformance/README.md).
They add no requirements.

## Not yet available

These remain follow-ups in the [plan](../specs/006-protein-header/plan.md):

- JSON-LD and HTML microdata forms (F-01). A reviewed FHP HTML microdata binding (rules F1–F7 over the shared [MICRODATA.md](MICRODATA.md) M1–M5) lives in [FHP-Specification](https://github.com/FAIR-bioHeaders/FHP-Specification/blob/main/docs/FHP-MICRODATA.md) and is the binding named as authoritative for FHP in that page's [Type-specific bindings](MICRODATA.md#type-specific-bindings) table (#216 reading 1, merged as #217); the FHP canonical JSON-LD context and reading rules live in FHP-Specification as well, still labeled draft there, with shared publication coordinated through #107 ([JSONLD.md](JSONLD.md) documents the FHR form only). The toolkit reader/writer for both forms shipped in fair-bioheaders 0.8.2 (Tools#58, merged in Tools#98): `convert` reads and writes FHP canonical JSON-LD and typed HTML microdata. FHP has no schema.org export profile and no shared conformance vector covers its typed forms; no website support is claimed here.
- Checking GFF3 parents (F-03, spec 007).

F-05 (the persistent schema alias) and F-07 (the release) are complete: v0.4.0 is tagged,
and `https://w3id.org/fair-bioheaders/fhp/vX.Y.Z` selects that release's `fhp.json`
(registered in perma-id/w3id.org#6868).

**Release line (maintainer decision, 2026-10-11).** FHP v0.1 was released from the
`release-v0.4` line, with FAIR-bioHeaders-Specification v0.4.0, so it starts with the tightened
core patterns (anchored ORCID and taxon URLs, padded checksums, bare DOIs) and the optional
author `nameType`. Its persistent schema URL is
`https://w3id.org/fair-bioheaders/fhp/vX.Y.Z`, where `vX.Y.Z` is the
FAIR-bioHeaders-Specification release tag, as for `/fhr/vX.Y.Z`; it serves the v0.4.0 release.
`fhp.json` on `main` is generated from the same v0.4 core, not the core's v0.3 patterns.
