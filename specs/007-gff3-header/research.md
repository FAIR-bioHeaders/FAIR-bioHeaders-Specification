# Research: GFF3 annotation header (FHGFF3)

**Feature**: 007-gff3-header | **Date**: 2026-10-13 | **Spec**: [spec.md](spec.md) (clarified 2026-10-13)

Observations about real practice are in [research-notes.md](research-notes.md) (G-01 to G-07).
This file records the design decisions, each with its rationale and the alternatives considered.
It follows FHP (specs/006-protein-header/research.md) wherever the two types share a question.

## D-01 Files and layout

**Decision**:
- `fhgff3_linkml.yml` (repository root) imports `schemas/core.yaml` and a new shared module,
  `schemas/shared.yaml` (D-04).
- `fhgff3.json` is generated by `json-schema-generator.py --type fhgff3` and committed. Its review
  baseline is `.github/schema-baseline-fhgff3.json`.
- Examples go in `examples/fhgff3/`, the format document is `docs/FHGFF3.md`, and the conformance
  vectors use the format name `fhgff3`.

**Rationale**: This is FHP's layout (006 D-01), so the shared tooling (`check_linkml.py`,
`check_schema_drift.py`, `check_release.py`) extends by one entry per type.

**Alternatives**: A hand-written `fhgff3.json`, or a separate repository. Both are rejected for
the reasons in 006 D-01. Reusing files from the FHGFF3 fork is excluded by its unresolved upstream
licence (#75).

## D-02 Header type discrimination

**Decision**: The FHGFF3 schema constrains `schema` to a raw GitHub URL of
`FAIR-bioHeaders/FAIR-bioHeaders-Specification/<ref>/fhgff3.json`. Tools select FHGFF3, FHP or FHR from the
`schema` URL, in that order, and default to FHR.

**Rationale**: This is 006 D-02 with one more type. FHR stays the default, so FHR and FHP behaviour
is unchanged.

**Alternatives**: Selecting by container (`.gff3` means FHGFF3). Rejected: a GFF3 file citing
`fhr.json` must be validated as FHR and fail, as a protein FASTA citing `fhr.json` does (006 P2).

## D-03 The genome link

**Decision**:
- **Checksum form**: a core `derivedFrom` item with `headerType: FHR` and
  `relationship: annotates`.
- **Reference form**: a new `genomeReference` object with `accession` (required), `seqcol_id`
  (required, the core slot and its pattern) and `assemblyName` (optional).
- **Schema rule**: at least one form must be present, and at most one `derivedFrom` item may have
  `relationship: annotates`. LinkML cannot express "an array contains an item with these values",
  so the generator adds the rule to `fhgff3.json` as post-processing (contracts/fhgff3-schema.md
  step 5):
  - `anyOf: [{required: [genomeReference]}, {required: [derivedFrom], properties: {derivedFrom:
    {contains: …}}}]`;
  - `maxContains: 1` for `annotates` items.
- **Both forms present**: allowed, for the same genome. The checksum is authoritative.
  `verify-links` verifies the checksum, and also compares `genomeReference` with the supplied
  genome's own FHR header where it can. A disagreement is reported as `not matched` for the
  reference.

**Rationale**:
- These are Adam's 2026-10-13 answer and #54.
- The core is unchanged, so `derivedFrom` stays checksum-only and every `derivedFrom` item is
  verifiable. That matches FHP's `source` decision.
- Allowing both lets a producer who has an FHR genome also record the public accession and SeqCol
  digest that others can resolve. Making the checksum authoritative keeps one verifiable identity.

**Alternatives**:
- Exactly one form (`oneOf`): this forbids useful redundancy and gains nothing.
- An optional checksum in the core `derivedFrom`: rejected by the maintainers (core change, blurs
  verified and asserted links).
- The genome in `source`: `source` is optional and cannot carry the requirement.

## D-04 Shared objects outside the core

**Decision**:
- Move FHP's `Software`, `Source` and `Completeness` classes and the `BuscoMode` enum from
  `fhp_linkml.yml` into `schemas/shared.yaml`. `fhp_linkml.yml` and `fhgff3_linkml.yml` import it.
- `schemas/core.yaml` and `fhr.json` are unchanged.
- `fhp.json` must stay byte-identical, and a test checks this.

**Rationale**:
- FHGFF3 needs the same software, source and completeness shapes (spec FR-008). Two copies would
  drift.
- FHP follow-up F-06 said to promote `Software` when a second type needs it. A separate module
  does that without touching the core that FHR imports, so FHR's generated schema cannot change.

**Alternatives**:
- Promote the classes to `schemas/core.yaml`: the core is FHR's import, and a change there needs
  the FHR equivalence and drift checks to prove nothing moved. That is possible later, but
  unnecessary now.
- Duplicate the classes in `fhgff3_linkml.yml`: rejected (drift).

## D-05 FHGFF3 fields

**Decision**:
- **Required**: the core's required slots, plus `annotation` (`sdo:name`), plus the genome link
  (D-03).
- **Optional**:
  - `genomeReference` (D-03);
  - `derivedFrom` (core);
  - `source` (shared);
  - `annotationSoftware` (list of shared `Software`);
  - `annotationProtocol` (URI);
  - `soVersion` (string; the SO `data-version`, for example `2026-08-07`);
  - `featureCounts` (list of `{featureType, count}`);
  - `completeness` (shared);
  - the core's optional `voucherSpecimen`, `accessionID`, `scholarlyArticle`, `documentation`,
    `identifier`, `relatedLink`, `funding` and `reuseConditions`.
- `featureType` is the type as written in column 3 of the file: an SO term name such as `mRNA`, or
  an accession such as `SO:0000234`. Its pattern is non-empty with no whitespace.
- `soVersion` is free text with a documented example, not a date pattern. Older SO releases used
  numbers such as `2.5.3`, and a pattern would reject honest values.

**Rationale**:
- Spec FR-008 and FR-013: no required method field.
- A list of `{featureType, count}` is closed, has a JSON Schema and a LinkML form, and maps to
  JSON-LD later. A YAML map keyed by type would need open properties.

**Alternatives**:
- `featureCounts` as a map: rejected (open object, against FR-009).
- Fixed `geneCount`/`mRNACount` keys: these miss ncRNA and pseudogene annotations, and invent a
  vocabulary.

## D-06 Placement rule and toolkit scanner

**Decision**:
- Rule **G1** (docs/FHGFF3.md) is spec FR-001.
- The toolkit's leading-block scanner gains a GFF3 mode. It is the GFA scan (the block ends at the
  first nonblank line that is not a `#` line) plus two changes:
  - a line starting with `##FASTA` also ends the block;
  - a `#~` line on line 1 is an error ("the header must follow ##gff-version").
- Checksum, strip and the late-`#~` check reuse the GFA code paths.
- `combine` writes line 1 of the body (which must start with `##gff-version 3`), then the header
  lines, then the rest of the body. The checksum is computed over the bytes in that order.

**Rationale**:
- One scanner keeps FASTA, GFA and GFF3 consistent.
- The `##FASTA` end is the only GFF3-specific difference, and the validator already states it
  (HDR-004).

**Alternatives**:
- A separate GFF3 parser: rejected (two parsers drift).
- Ending the block at any `##` directive: rejected, because #54 allows `##sequence-region` among
  header lines.

## D-07 Native-directive cross-check

**Decision**:
- **Library**: a function `gff3_directives(lines)` reads the native lines of the leading block,
  and `cross_check(metadata, directives)` returns warnings.
- **The three pairs** (spec FR-011):
  - **taxon**: the numeric ID from `taxon.uri` (`identifiers.org/taxonomy:N`) against the ID in
    `##species` (`…taxonomy:N`, `…?id=N`, or `…/N`);
  - **accession**: `genomeReference.accession`, or the `annotates` item's `accessionID.name`,
    against `#!genome-build-accession`, with a leading `NCBI_Assembly:` (or other `WORD:`) prefix
    removed. The comparison is exact, version included;
  - **assembly name**: `genomeReference.assemblyName` against the last whitespace-separated token
    of `##genome-build` and of `#!genome-build`.
- **Results**: values that differ give a warning naming both. A value missing on either side is
  not compared. A directive whose value cannot be parsed gives a "not checked" note.
- **Where reported**: `validate` and `verify` print warnings on standard error as
  `FHR: warning: …` and keep their exit status. `verify-links` and `assess` include them. The
  gff3-validator reports them as rule HDR-010 (warning).

**Rationale**: Adam's 2026-10-13 answer. Comparing numbers and accessions avoids false alarms from
URL forms (NCBI's browser URL against identifiers.org).

**Alternatives**: Treating disagreement as an error: rejected (the answer said warnings; native
lines are often stale in copied files).

## D-08 `verify-links` for GFF3

**Decision**:
- GFF3 files are accepted as FILE and as PARENT.
- A parent's family checksum is computed from its bytes (R1–R4, GFF3 mode), and its header type is
  read from its `schema`.
- The `annotates` item is checked like any `derivedFrom` item (006 contracts/cli.md).
- **`genomeReference`**: compared with each supplied parent whose header type is FHR and whose
  header records a `seqcol_id`:
  - `matched` when the SeqCol digests are equal (and the accessions, if both are recorded);
  - `not matched` when the digests differ;
  - `not checked` otherwise, with the reason (no FHR genome supplied, or no SeqCol digest
    recorded).

  It never computes a SeqCol digest.
- The output line for the reference is `genomeReference <accession>: <status>`.

**Rationale**: FR-015. An accession plus SeqCol is an assertion. It can be compared only with
another assertion of the same kind, and never computed from bytes in v0.1.

## D-09 Serialisations

**Decision**:
- JSON, YAML and the embedded GFF3 header are supported.
- JSON-LD and microdata for FHGFF3 are refused, with FHP's message naming FHGFF3. This is follow-up
  F-01, extended.
- The LinkML slots carry `slot_uri` annotations from the start.

**Rationale**: The same as 006 D-08. `make_jsonld.py` is FHR-only.

## D-10 Conformance vectors

**Decision**:
- Format `fhgff3`, generated by `scripts/make_conformance.py` with the standard library only. The
  metadata is written as dicts and the headers as literal `#~` text, with no PyYAML (the FHP CI
  lesson).
- Expected checksums use `hashlib` over the vector bytes, as for every other format.
- **Valid vectors**:
  - native directives before, among and after `#~` lines;
  - `###` before features;
  - `##FASTA`;
  - a header-only file;
  - `##gff-version 3.1.26`;
  - gzip and BGZF;
  - CRLF;
  - a checksum genome link, a reference genome link, and both;
  - a nested parent checksum.
- **Invalid vectors**:
  - a `#~` line after a feature, after `##FASTA`, and in a concatenated second file;
  - a header before `##gff-version`;
  - no genome link;
  - half a reference;
  - two `annotates` items;
  - `annotates` with header type FHP;
  - an FHR-only key;
  - two checksum lines.
- Rule labels: R1–R10 and G1–G3.

**Rationale**: FR-019, #50. The shared manifest and checkers already handle formats (006 D-09).

## D-11 gff3-validator integration

**Decision**:
- The validator keeps its existing design. Core validation never imports the toolkit, and header
  checks use the optional `headers` extra (`fair-bioheaders`).
- HDR-004 to HDR-010 run when the installed toolkit has FHGFF3 support (feature-detected by
  `bioheaders.FHGFF3_SCHEMA`). Otherwise HDR-002 is reported as now.
- The extra's range becomes `>=0.5,<0.7`, so the release that adds FHGFF3 (0.6.0) satisfies it.
- Until that release, the validator's CI installs the toolkit from a pinned `main` commit for the
  header tests. Its PyPI release waits for toolkit 0.6.0.
- The browser build keeps reporting HDR-002. Bundling the toolkit into the Pyodide build is
  follow-up F-04.
- HDR-010 (warning, layer `fhgff3`) is the native-directive cross-check.

**Rationale**:
- "No second parser" (spec FR-021).
- The validator's no-network, toolkit-optional design is preserved, and plain GFF3 is unaffected
  (FR-016).

**Alternatives**:
- Vendoring the schema and scanner into the validator: rejected (a second parser, and drift).
- A hard dependency on the toolkit: rejected (it breaks the toolkit-free core and the browser
  build).

## D-12 Examples and placeholders

**Decision**:
- **Examples**: synthetic genome and annotation sequences, a synthetic FHR genome
  (`examples/fhgff3/genome.fhr.fasta`) whose real checksum the linked examples cite, and
  placeholder accessions and SeqCol digests. The placeholders are labelled as such in
  `docs/FHGFF3.md` and in `documentation`.
- **Public identifiers** appear only where accurately described: the GFF3 directive forms of
  NCBI and Ensembl (research G-02, G-03) are shown in docs as quotations with fetch dates, not as
  claims about the examples.

**Rationale**: Constitution IV (no invented metadata), and FR-018.

## D-13 Branches and release

**Decision**:
- FHGFF3 is developed on `main`. It joins `release-v0.4` at the next main → `release-v0.4` sync,
  done by the coordinator. FHGFF3 v0.1 is released with FAIR-bioHeaders-Specification v0.4.0, as FHP is.
- The w3id alias `/fair-bioheaders/fhgff3/vX.Y.Z`, the release and the website entry are
  maintainer follow-ups.

**Rationale**: The maintainer decision for FHP (2026-10-11), applied to the next type.

## D-14 Toolkit version

**Decision**:
- GFF3 support is added on toolkit `main` and released as 0.6.0 by a maintainer action, not by
  this feature.
- The bundled `fhgff3_schema.json` is a byte-identical copy of `fhgff3.json`, checked by
  `check_release.py`.

**Rationale**: The same as FHP's bundling (006 D-10). Releases are outside the feature's tasks.
