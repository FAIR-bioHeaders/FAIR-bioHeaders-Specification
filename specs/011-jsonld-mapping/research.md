# Research: JSON-LD mapping and serialisation (Phase 0)

**Feature**: 011-jsonld-mapping | **Date**: 2026-10-10 | **Plan**: [plan.md](plan.md) | **Spec**: [spec.md](spec.md)

This document resolves every unknown in the plan's Technical Context. Each entry gives the
decision, the rationale and the alternatives considered. Sources are cited inline with URLs.
Vocabulary facts were checked on 2026-10-10 against:

- **schema.org v30.1**, the current release (<https://schema.org/docs/releases.html#v30.1>),
  using the machine-readable release file
  <https://schema.org/version/latest/schemaorg-current-https.jsonld> and the official JSON-LD
  context <https://schema.org/docs/jsonldcontext.jsonld>;
- the **Bioschemas** profile index <https://bioschemas.org/profiles/>;
- **DCMI Metadata Terms** <https://www.dublincore.org/specifications/dublin-core/dcmi-terms/>;
- **JSON-LD 1.1** <https://www.w3.org/TR/json-ld11/> and the **JSON-LD 1.1 Processing
  Algorithms and API** <https://www.w3.org/TR/json-ld11-api/>.

Phase 0 included a throw-away prototype, which is not committed. It ran the draft context
([contracts/fhr.context.jsonld](contracts/fhr.context.jsonld)) with PyLD 3.3.0 on Python 3.13
and PyLD 2.0.4 on Python 3.9, over both examples, the YAML example and the 30 metadata headers of
the valid conformance vectors. Its findings are cited below as "prototype".

Two repositories are involved:
- **FAIR-bioHeaders-Specification** is this repository.
- **FAIR-bioHeaders-Tools** is the `fair-bioheaders` distribution. Its import name and command are
  `bioheaders`, and the local checkout is `../FHR-File-Converter`.

**Rationale**:
- Constitution I (both repositories): the specification defines the mapping, and the toolkit
  implements it with byte-identical copies.
- #56 suggests `mappings/` and `docs/mappings/` for crosswalks
  (<https://github.com/FAIR-bioHeaders/FAIR-bioHeaders-Specification/issues/56>). A top-level `mappings/`
  directory starts that layout without moving the existing `fhr_mappings.yml`.
- `jsonld/` keeps the context and the vocabulary in one directory that a release URL can address
  (R-09).

**Alternatives considered**:
- *Context only in the toolkit.* Rejected: FR-001 says the specification publishes the context,
  and toolkit constitution I forbids defining behaviour there first.
- *Putting the files under `schemas/`.* Rejected: `schemas/` holds LinkML modules that are
  imported. Generated JSON-LD files beside them would invite a by-hand edit of a generated file.

## R-02. Mapping-kind vocabulary and its direction

**Decision**: Use seven kinds. They are the union of #56's list ("exact, conditional,
narrower/broader, lossy, or unsupported") and the spec's US2 list ("exact, broader, narrower,
related, unsupported"):

| Kind | Meaning (the target term relative to the FHR field) | SKOS / LinkML equivalent |
|---|---|---|
| `exact` | Same meaning and the same subject; the value copies unchanged | `skos:exactMatch` / `exact_mappings` |
| `broader` | The target term is broader than the FHR field. The FHR value is a valid value of the target, but the target means more | `skos:broadMatch` / `broad_mappings` |
| `narrower` | The target term is narrower. Only some FHR values qualify | `skos:narrowMatch` / `narrow_mappings` |
| `related` | Associated, but neither broader nor narrower. Not used to carry the value | `skos:relatedMatch` / `related_mappings` |
| `conditional` | Correct only when a stated condition holds (for example, the value identifies a licence). The `condition` field is required | none: procedural (#56: "do not represent procedural transformations as unconditional LinkML exact_mappings") |
| `lossy` | The value can be carried, but information is lost. The `loss` field is required | none |
| `unsupported` | There is no term in the target vocabulary | SSSOM `sssom:NoTermFound` |

The direction is always **target relative to source**, as in SKOS and LinkML. The existing
`fhr_mappings.yml` uses the opposite wording for one entry: `assemblyProtocol` → MIxS `sop`
is `relationship: narrow`, meaning "FHR is narrower", while `fhr_linkml.yml` records the same
pair as `broad_mappings`. In this table that pair is `broader`. `fhr_mappings.yml` stays unchanged,
because `scripts/project_mixs.py` and its tests read it, and the mapping-table contract
documents the equivalence.

**Rationale**: One vocabulary serves #56 and this feature. The SKOS direction matches LinkML,
which is the semantic source (R-08). SKOS mapping properties:
<https://www.w3.org/TR/skos-reference/#mapping>. SSSOM "no term found":
<https://mapping-commons.github.io/sssom/>.

**Alternatives considered**:
- *#56's list only.* Rejected: the spec's independent test names `related`.
- *Source-relative direction, as `fhr_mappings.yml` has it.* Rejected: it contradicts the LinkML
  slot annotations of the same pair.

**Counts**:
- **The JSON-LD terms.**
  - 20 of the 45 paths map to schema.org terms: 12 top-level and 8 nested. All 14 distinct
    schema.org properties used are core; of the 5 schema.org classes used, only `sdo:Taxon` is
    pending.
  - 3 nested paths (`taxon.uri`, `metadataAuthor[].uri` and `assemblyAuthor[].uri`) become node
    identifiers (`@id`).
  - 22 paths map to FHR terms: 12 top-level, the 9 `vitalStats` fields and `commandLineOption`.
- **The DCMI column.**
  - 19 of the 45 paths have a DCMI term: 14 of the 24 top-level fields and 5 nested.
  - 26 paths have "none", each with a reason.
  - Of the 19 DCMI mappings, 6 are `exact`, 2 `broader` and 11 `conditional`.

**Rationale**:
- Every schema.org term above is checked against the domains in the v30.1 release file. Each
  property is used only on a node whose type is in its `domainIncludes`, directly or through a
  superclass (Dataset → CreativeWork → Thing). The Bioschemas profiles for Dataset, Taxon,
  ComputationalTool and Person choose the same terms (R-04).
- An FHR term is used wherever schema.org has no term, or where the closest term has the wrong
  domain (`relatedLink`, `instrument`), the wrong subject (`sdPublisher`) or the wrong meaning
  (`sha256`). Constitution IV forbids forcing those.
- The DCMI column follows #56's conditional crosswalk wording, so the #56 work starts from the
  same conditions (SC-004).

**Alternatives considered**:
- *`sdo:author` for `assemblyAuthor`.* Rejected: `creator` is declared equivalent to
  `dct:creator`, and the Bioschemas Dataset profile uses it.
- *`sdo:taxonomicRange` for `taxon`.* Rejected: pending, and it is a domain violation on Dataset.
- *`sdo:relatedLink` and `sdo:instrument`.* Rejected: domain violations that a schema.org
  validator reports.
- *Mapping `metadataAuthor` to `sdo:sdPublisher`.* Rejected: it means "the party responsible for
  generating and publishing the current structured data markup", which is not authorship of an
  FHR record.
- *`documentation` as a new FHR term.* It was considered and kept as an option. `sdo:description`
  is what search engines and the Bioschemas Dataset minimum need, and the condition is recorded.
  Open question 3 in the plan.

## R-04. Types and Bioschemas profiles (FR-006)

**Decision**: The toolkit adds `@type` to the record and to every nested resource. The rules are:

| Node | `@type` | Rule |
|---|---|---|
| Record (root) | `Dataset` → `sdo:Dataset` | Always |
| `taxon` | `Taxon` → `sdo:Taxon` (pending) | Always |
| `metadataAuthor[]`, `assemblyAuthor[]` | `Person` → `sdo:Person` | When the item's `uri` is an ORCID iD. The schema allows only ORCID URIs there, and ORCID is "a unique, persistent identifier for individuals" (<https://info.orcid.org/what-is-orcid/>) |
| `metadataAuthor[]`, `assemblyAuthor[]` | `Organization` → `sdo:Organization` | When the item's `uri` is a ROR ID (maintainer decision 4, R-18). `fhr.json` does not allow ROR URIs yet (T047) |
| `metadataAuthor[]`, `assemblyAuthor[]` | `Agent` → `fhr:Agent` | Otherwise. FHR says "Person or Org" and records which only through an identifier. `fhr:Agent` is defined as "a person or organization that the FHR record does not classify" (`skos:closeMatch dcterms:Agent`) |
| `accessionID` | `PropertyValue` → `sdo:PropertyValue` | Always (schema.org's way to type an identifier) |
| `assemblySoftware[]` (objects) | `SoftwareApplication` → `sdo:SoftwareApplication` | For each object item. A legacy string is a literal, not a node |
| `vitalStats` | `VitalStats` → `fhr:VitalStats` | Always |

The `identifier[]` values stay literal compact identifiers. Typing them would require changing
FHR values, which FR-007 forbids, and Bioschemas recommends CURIE text for `identifier`. FR-006
is met for identifiers through `accessionID`.

The record **follows** the Bioschemas profiles' property choices but does **not claim
conformance**. It emits no `dct:conformsTo`, because FR-007 and FR-009 allow only FHR keys plus
`@context` and `@type`. The minimum properties that FHR cannot supply are:

| Profile | Minimum properties FHR lacks |
|---|---|
| Dataset 1.0-RELEASE (<https://bioschemas.org/profiles/Dataset/1.0-RELEASE>) | `@id`, `dct:conformsTo`, `keywords` and `url`, always (`@id` is in the profile's minimum list too; checked on 2026-10-10 against the profile page). `description`, `license` and `identifier` are present only when `documentation` (as text), `reuseConditions` and `identifier` are |
| Taxon 1.0-RELEASE (<https://bioschemas.org/profiles/Taxon/1.0-RELEASE>) | `dct:conformsTo`, `taxonRank` |
| ComputationalTool 1.0-RELEASE (<https://bioschemas.org/profiles/ComputationalTool/1.0-RELEASE>) | `dct:conformsTo`, `description` |
| Person 0.3-DRAFT (<https://bioschemas.org/profiles/Person/0.3-DRAFT>) | `dct:conformsTo`, `description`, `mainEntityOfPage` |

There is no Bioschemas profile for genome assemblies. The profile list was checked on
2026-10-10 (<https://bioschemas.org/profiles/>).

**Rationale**:
- FR-006 requires typed resources. The type follows the evidence: ORCID implies a person, and
  without ORCID nothing implies one, so constitution IV rules out guessing Person or Organization
  (#56: "Person/organization classification is supplied explicitly; it is not inferred from the
  name string").
- Claiming Bioschemas conformance would be false: the minimum properties are missing.

**Alternatives considered**:
- *Typing name-only authors as `sdo:Person`.* Rejected: it invents a classification.
- *`dcterms:Agent` as the type.* Rejected: SC-003 limits expanded terms to schema.org, Bioschemas
  and FHR. `fhr:Agent` records the closeness in the vocabulary.
- *Adding `dct:conformsTo`, `keywords` and `url`.* Rejected: these are not FHR keys (FR-007), and
  they would be invented values. A portal can add them around the record. Open question 2 in the
  plan covers whether FHR should gain them.
- *An additional FHR record class beside `Dataset`.* Rejected for release 1. The Bioschemas
  profiles prefer a single type, and nothing consumes a second one yet.

## R-05. Namespaces and prefixes

**Decision**:
- **schema.org terms use `http://schema.org/`**, the namespace in schema.org's own JSON-LD context
  (`"@vocab": "http://schema.org/"` in <https://schema.org/docs/jsonldcontext.jsonld>). Documents
  that use `"@context": "https://schema.org"` therefore expand to the same IRIs as FHR records.
- **The prefix is `sdo`, not `schema`.** `schema` is an FHR key, and a term cannot be both an
  FHR property and a prefix: an expanded term definition is not usable as a prefix in JSON-LD 1.1
  (<https://www.w3.org/TR/json-ld11/#compact-iris>).
- **FHR terms use `https://w3id.org/fair-bioheaders/terms#`** (FR-008), unversioned. The local
  name equals the LinkML slot or class name, for example `fhr:seqcol_id` and `fhr:VitalStats`.

**Rationale**: The http namespace matches what schema.org consumers get from schema.org's own
context, so the graphs merge. The `sdo` prefix is a common alias for schema.org, and it avoids the
key collision. Using the slot name as the local name makes the IRI derivable from LinkML (R-08).

**Alternatives considered**:
- *`https://schema.org/`.* Rejected: schema.org's context still maps the vocabulary to http, and
  graphs would not merge. Consumers that normalise both still work.
- *A versioned FHR namespace.* Rejected by the clarification (FR-008).

## R-06. JSON-LD 1.1 mechanics

**Decision**: The context ([contracts/fhr.context.jsonld](contracts/fhr.context.jsonld)) is a
JSON-LD 1.1 context with these rules.

1. **`@version: 1.1` and `@protected: true`.** A later context cannot silently redefine an FHR
   key; it fails with "protected term redefinition" (prototype). A portal that combines contexts
   must put FHR's last.
2. **Property-scoped contexts for every nested object**: `taxon`, both author lists,
   `accessionID`, `vitalStats` and `assemblySoftware`. Each scoped context starts with `null` and
   then redeclares the prefixes, the node's type terms and its own keys. Nested objects therefore
   do not inherit top-level terms, so a key such as `name` or `version` means `sdo:name` or
   `sdo:softwareVersion` only where FHR defines it. Property-scoped contexts may override
   protected terms (<https://www.w3.org/TR/json-ld11/#protected-term-definitions>).
3. **`uri` becomes a keyword alias for `@id`** inside `taxon` and the author lists. In
   `assemblySoftware`, `uri` is `sdo:url` with `@type: @id` instead (R-03 row 41).
4. **IRI coercion (`@type: @id`)** applies only to fields whose schema requires an absolute URI:
   `schema`, `relatedLink[]`, `assemblyProtocol`, `accessionID.url` and
   `assemblySoftware[].uri`. **Fields that may hold an identifier or free text stay literals**:
   `identifier[]` (compact identifiers), `scholarlyArticle` (a bare DOI), `documentation`,
   `reuseConditions`, `funding`, `voucherSpecimen` and `accessionID.name`. A context cannot coerce
   a value conditionally, and coercing a non-IRI string gives a wrong IRI. `@base` cannot help:
   it is ignored in remote contexts (JSON-LD 1.1 API, Context Processing step 5.7).
5. **Containers**:
   - `@set` on every array-valued key (`genomeSynonym`, both author lists, `instrument`,
     `identifier`, `relatedLink` and `assemblySoftware`), so a one-element array stays an array.
   - `@list` on `commandLineOption`, where order is meaningful. Its LinkML source is
     `list_elements_ordered: true`.
6. **Datatypes**:
   - `dateCreated` is coerced to `xsd:date`.
   - Numbers stay native JSON. JSON-LD gives `xsd:integer` for integral values and `xsd:double`
     otherwise (<https://www.w3.org/TR/json-ld11-api/#data-round-tripping>). Explicit integer
     coercion adds nothing.
   - `masking` stays a literal and not an `@vocab` enumeration. Its schema pattern is unanchored,
     so a valid value is not guaranteed to be one of the five tokens, and a token IRI would need
     enumeration terms that FHR does not yet define.
7. **Injectivity.** In each scope no two FHR keys map to the same IRI. This is why
   `accessionID` uses `fhr:accessionID` and not `sdo:identifier`. JSON-LD term selection would
   otherwise compact every value into the `@set` term `identifier`, losing `accessionID`
   (<https://www.w3.org/TR/json-ld11-api/#term-selection>). The generator checks this.
8. **FHR keys unchanged** (FR-007). Every FHR key is a term, there is no `@vocab`, and no key is
   renamed. Unknown keys are not silently given an IRI.

**Rationale**: The prototype round-tripped every record (R-12) and showed that PyLD 2.0.4 and
3.3.0 give byte-identical expansions with this context. Every expanded predicate was in
`http://schema.org/`, `https://w3id.org/fair-bioheaders/terms#` or `rdf:` (SC-003).

**Alternatives considered**:
- *A flat context, with no scoped contexts.* Rejected: `name`, `uri` and `version` mean
  different things in different objects (R-08 shows LinkML's flat output).
- *Type-scoped contexts.* Rejected: the types are added by the toolkit, and a third-party
  document without them would lose the nested mappings. Property-scoped contexts depend only on
  FHR keys.
- *`@list` for the author lists.* Rejected: schema.org consumers expect `creator` to point at
  Person or Organization nodes, not at an `rdf:List`. The order is kept in the JSON-LD document,
  and the RDF loss is recorded (R-12).
- *Scoped contexts that inherit top-level terms.* Rejected: in the prototype the conformance
  vector `fasta-nested-checksum` put `taxon.checksum` on the taxon node as `fhr:checksum`, the
  file-checksum predicate, which is a false statement.

## R-07. Open nested objects and keys without a term

**Decision**: `taxon`, the author items, `accessionID` and `vitalStats` are open in `fhr.json`:
they have no `additionalProperties: false`. A record may therefore carry nested keys that FHR
does not define. The conformance vectors `fasta-nested-checksum` and `gfa-nested-checksum` do
this.

- **Writing.** These keys stay in the JSON-LD document, so the canonical round trip is exact
  (SC-001). They have no term, so JSON-LD processors drop them. The toolkit prints one warning per
  key to stderr, for example
  `FHR: JSON-LD: taxon.checksum has no JSON-LD term; linked-data consumers will ignore it`.
  The output is still written.
- **Reading through the canonical path (rule J1).** These keys are kept, as JSON reading keeps
  them.
- **Reading through the general path (rule J4).** A term that expansion drops, or an IRI that
  maps to no FHR field, is reported by name. The document is invalid unless
  `--ignore-unknown-terms` is given, in which case each one is still reported (spec edge case:
  "reported, not silently dropped").

**Rationale**: This preserves user data (toolkit constitution IV) and fails closed on input that
is ambiguous as FHR (toolkit constitution III).

**Alternatives considered**:
- *Refusing to write records with extra nested keys.* Rejected: they are valid FHR, and JSON,
  YAML and microdata all keep them.
- *Mapping extra keys under `@vocab`.* Rejected: it invents terms (constitution IV).

## R-08. LinkML as the single source; evaluation of `gen-jsonld-context`

**Decision**: LinkML annotations are the **single source of the term IRIs**. A small repository
script, `scripts/make_jsonld.py`, generates the context and the vocabulary from them. It does
not use `gen-jsonld-context` as is. The LinkML changes add only annotations, so
`scripts/check_linkml.py` still passes (verified in the prototype):

- **Prefixes.** In both `schemas/core.yaml` and `fhr_linkml.yml`: `sdo: http://schema.org/`,
  `fhr: https://w3id.org/fair-bioheaders/terms#` and `xsd:`. `default_prefix` changes from `ex`
  (`https://example.org/`) to `fhr`, so every slot without a `slot_uri` gets its FHR term IRI
  automatically.
- **`slot_uri`** for the 20 schema.org mappings, including `name`, `uri` and `version`
  separately on each class.
- **`class_uri`**: FHR → `sdo:Dataset`, Taxon → `sdo:Taxon`, Author → `fhr:Agent`,
  AccessionID → `sdo:PropertyValue`, AssemblySoftware → `sdo:SoftwareApplication`,
  VitalStats → `fhr:VitalStats`.
- **Two annotations**: `jsonld_node_id: true` on `Taxon.uri` and `Author.uri`, and
  `jsonld_type_if_uri: sdo:Person` on `Author`.
- **`list_elements_ordered: true`** on `commandLineOption`.
- **Two vocabulary links**: `broad_mappings: [sdo:identifier]` on `accessionID`, emitted as
  `rdfs:subPropertyOf`, and `close_mappings: [dcterms:Agent]` on `Author`, emitted as
  `skos:closeMatch` (with a `dcterms:` prefix).
- **`uri: xsd:string`** on the core type `sha2`.
- **Descriptions** for slots that have none in LinkML (`N90`, `gcContent`, the AssemblySoftware
  attributes), copied from `fhr.json`. FR-002 needs a description for every FHR term. This changes
  no constraint.

`make_jsonld.py` reads `SchemaView` induced slots per class and builds the property-scoped
context described in R-06:
- multivalued → `@set`;
- `list_elements_ordered` → `@list`;
- range `uri` → `@type: @id`;
- range `date` → `xsd:date`;
- a class range → a scoped context.

It writes `jsonld/fhr.context.jsonld`, `jsonld/terms.ttl` and `docs/TERMS.md`. With `--check` it
fails on drift, as `check_linkml.py` does. The DCMI column and the notes live in the mapping table
(R-15). A test asserts that the table's JSON-LD term for every path equals the LinkML-derived IRI.

**Evaluation of `gen-jsonld-context`** (LinkML 1.11.1, the version pinned in
`requirements-linkml.txt`):

| Finding | Effect |
|---|---|
| It fails on the current model: `ValueError: type "sha2" does not declare a URI` | It cannot run until `sha2` has `uri:`. That is a harmless fix, and it is included above |
| It flattens attributes by name: `Taxon.name` (`sdo:name`) and `AccessionID.name` (a different `slot_uri`) became a single global `name` term | Different IRIs for the same key in different classes cannot be expressed, which R-03 rows 18 and 41 need |
| `identifier: true` on `Taxon.uri` gives a **global** `"uri": "@id"` | It would make `assemblySoftware[].uri` an `@id` too. It also makes `uri` required, which changes the generated JSON Schema (constitution I and II) |
| It emits `"@vocab": "https://example.org/"` (from `default_prefix: ex`) | Every unknown key would silently get an example.org IRI |
| It puts `"@type": "@id"` on inlined object slots and `xsd:float` on `schemaVersion`; there are no type terms for instances and no property-scoped contexts | It does not match R-06 |

**Rationale**:
- LinkML stays authoritative for meaning (spec 004 Assumptions: "LinkML ... is the source of
  truth; generated artefacts are committed and drift-checked as today").
- `fhr.json` stays the validation contract (constitution I).
- The generator is small and specific to FHR, like `json-schema-generator.py` and
  `project_mixs.py`.

Sources:
- LinkML JSON-LD context generator: <https://linkml.io/linkml/generators/jsonld-context.html>.
- `slot_uri`: <https://linkml.io/linkml-model/latest/docs/slot_uri/>.
- `list_elements_ordered`: <https://linkml.io/linkml-model/latest/docs/list_elements_ordered/>.

**Alternatives considered**:
- *`gen-jsonld-context` output as the published context.* Rejected for the reasons in the table.
- *A hand-written context with no LinkML link.* Rejected: two sources would diverge.
- *Putting the DCMI mappings in LinkML `*_mappings`.* Rejected for release 1. Most of them are
  conditional, and #56 warns against unconditional `exact_mappings` for these. The mapping table
  carries the conditions, and a later change may add the `exact` ones to LinkML.

## R-09. The context document: location, embedding, versioning, publication

**Decision**:
1. **Authoritative source.** `jsonld/fhr.context.jsonld` in FAIR-bioHeaders-Specification. Its canonical
   development URL is raw-main:
   `https://raw.githubusercontent.com/FAIR-bioHeaders/FAIR-bioHeaders-Specification/main/jsonld/fhr.context.jsonld`.
   This is consistent with the 2026-10-09 decision that raw-main is the single source of truth
   (spec#44 comment by molikd; website#15).
2. **Released copies.** These are addressable through the **existing** w3id rule
   `fhr/(vX.Y.Z)/(PATH)`, for example
   `https://w3id.org/fair-bioheaders/fhr/v0.5.0/jsonld/fhr.context.jsonld`, which redirects to
   the file at that release tag (<https://github.com/perma-id/w3id.org/tree/master/ids/fair-bioheaders>).
   No new registration is needed for the context.
3. **The toolkit embeds the context in every JSON-LD document it writes** (`"@context": {...}`,
   2.9 KB compact or about 4.8 KB pretty-printed). It does not reference a URL. When reading it
   accepts:
   - an embedded context equal to a bundled released context;
   - a reference to a known FHR context URL (raw-main or a w3id release alias) that maps to a
     bundled copy.

   It **never fetches** (FR-005).
4. **Versioning.**
   - The term IRIs never change (FR-008).
   - The context is versioned with FAIR-bioHeaders-Specification releases.
   - Within one FHR `schemaVersion` it changes only additively.
   - Changing an existing mapping is a breaking change to the linked-data view: it needs a
     changelog entry and a maintainer decision. Embedded copies keep old documents' meaning.
   - The toolkit bundles every released context, as spec#44 proposes for schemas.

**The tension, recorded**:
- **Raw-main is canonical** (website#15, spec#44, 2026-10-09). A URL reference to raw-main would
  change the meaning of old documents whenever main changes the context.
- **Versioned w3id aliases** (spec#44 decision of the same date, and Adam's proposal) give
  immutable targets, but the maintainers have not agreed a policy for using them as the *written*
  default (Adam's 2026-10-09 proposal awaits David's answer).
- **Neither URL is dereferenceable by a conformant JSON-LD processor.**
  `raw.githubusercontent.com` serves `text/plain; charset=utf-8` with `x-content-type-options:
  nosniff` (observed 2026-10-10), and w3id redirects to it. The JSON-LD 1.1 API says a document
  whose Content-Type "is neither application/json, application/ld+json, nor any other media type
  using a +json suffix" must be rejected with "loading document failed" (LoadDocumentCallback,
  <https://www.w3.org/TR/json-ld11-api/#loaddocumentcallback>). PyLD's requests loader is lenient,
  but jsonld.js and other strict processors are not. By contrast `https://json-ld.org/contexts/person.jsonld`
  is served as `application/ld+json`.

Embedding avoids all three problems: it needs no URL policy, it is immutable per document, and it
needs no fetch. The JSON-LD Best Practices draft also advises caching contexts rather than
fetching them (<https://w3c.github.io/json-ld-bp/#cache-json-ld-contexts>).

**Rationale**: This is the conservative choice. It adopts no unapproved URL policy, it keeps
raw-main authoritative, and every document works offline and indefinitely. A properly served
context URL can become the default later without changing any term (open question 1).

**Alternatives considered**:
- *Writing the raw-main URL.* Rejected: it is a moving target, and strict processors reject the
  content type.
- *Writing the w3id release alias.* Rejected for now: it depends on the open versioned-URL
  policy, on the content type, and on a release that contains the file.
- *Hosting on GitHub Pages (`fair-bioheaders.github.io`) with the right content type.* Deferred:
  it would make the website a publication point for specification artefacts, which website#15's
  "single source of truth" wording does not cover. This is open question 1.
- *A new w3id `context` rule now.* Deferred, for the same content-type reason.

## R-10. The vocabulary document and the w3id `terms` registration

**Decision**:
- **What is published.**
  - `jsonld/terms.ttl` (Turtle) is generated from LinkML. It has one `rdf:Property` or
    `rdfs:Class` per FHR term, with `rdfs:label`, `rdfs:comment`, `rdfs:isDefinedBy`,
    `sdo:domainIncludes` and `sdo:rangeIncludes`, and `rdfs:subPropertyOf` only where R-03 says
    so (`fhr:accessionID` → `sdo:identifier`).
  - `docs/TERMS.md` is generated from the same data as the human page. Each term is a heading
    whose text is exactly its local name, so GitHub gives it the anchor `#checksum`. A browser
    keeps the fragment across a redirect whose `Location` has none (RFC 9110 §10.2.2), so
    `https://w3id.org/fair-bioheaders/terms#checksum` lands on the term.
  - The format is in [contracts/vocabulary.md](contracts/vocabulary.md).
- **The w3id rule.** It goes in the existing `ids/fair-bioheaders/.htaccess`, administered by
  Adam Wright and David Molik. Adam or David submits it as a maintainer action; it is not
  submitted from this feature. The fragment never reaches the server, so the rule matches the
  path `terms`:

  ```apache
  # - https://w3id.org/fair-bioheaders/terms is the namespace of FAIR-bioHeaders
  #   vocabulary terms (https://w3id.org/fair-bioheaders/terms#checksum etc.).
  #   RDF clients asking for Turtle get the vocabulary file; everyone else gets
  #   its documentation page, where each term has an anchor.
  RewriteCond %{HTTP_ACCEPT} text/turtle
  RewriteRule ^terms/?$ https://raw.githubusercontent.com/FAIR-bioHeaders/FAIR-bioHeaders-Specification/main/jsonld/terms.ttl [R=302,L]
  RewriteRule ^terms/?$ https://github.com/FAIR-bioHeaders/FAIR-bioHeaders-Specification/blob/main/docs/TERMS.md [R=302,L]
  ```

  These rules go **before** the existing `fhr/` rules, and the header comment gains the bullet
  shown.
- **Requirements, from the w3id checker in the local clone (`tools/check`) and
  <https://w3id.org/docs/>.**
  - Contact block with a GitHub username: present.
  - HTTPS targets: yes.
  - No GitHub `/blob/` target for machine-readable files. The Turtle goes to raw; the `/blob/`
    target is the human documentation page, which the rule allows.
  - No catch-all 406: the last rule is an unconditional redirect to the documentation, as
    `htaccess/no-406-fallback` advises.
  - 302 rather than 301 (`htaccess/avoid-permanent-redirect`).
  - Only the own directory is changed.
  - Tested with the checker and a local Apache (`tools/server`) before the PR.
- **Raw-main for the vocabulary.** The vocabulary is unversioned by design (FR-008). The w3id
  rule documentation says "a branch is the right answer when you want whatever is current".

**Rationale**:
- FR-008 needs the namespace registered so that term IRIs resolve.
- Content negotiation to Turtle serves RDF tools, and the fallback serves people.
- The raw `text/plain` caveat (R-09) also affects Turtle clients that trust the Content-Type.
  This is recorded as a known limitation, and it is the same hosting question as open
  question 1.

**Alternatives considered**:
- *A JSON-LD rendering of the vocabulary as well.* Deferred. Turtle and the documentation page
  cover the RDF and human readers, and the context already serves the JSON-LD readers.
- *Slash namespace (`terms/checksum`).* Rejected by the clarification: it is `terms#`.

## R-11. Toolkit design: format dispatch, writer and readers (FR-005, FR-009)

**Decision**:
- **Dispatch.** Add `".jsonld": "jsonld"` to `FORMATS` and `"jsonld": "jsonld"` to
  `FORMAT_NAMES` in `bioheaders/cli.py`. Every command that reads or writes metadata then
  supports it through the existing `read_metadata`/`write_metadata` and `input_<format>` /
  `output_<format>` dispatch: `convert`, `validate`, the `--from`/`--to` options, `.jsonld.gz`,
  stdin and stdout. Add `fhr.input_jsonld(stream)` and `fhr.output_jsonld()` in
  `bioheaders/__init__.py`, delegating to a new module `bioheaders/jsonld.py`. The context is
  bundled as `bioheaders/fhr.context.jsonld`, loaded with `importlib.resources` like
  `fhr_schema.json`, and added to `pyproject.toml` `include`.
- **Writer** (`output_jsonld`). There is no processor and no new dependency.
  - The output is `{"@context": <bundled context object>, "@type": "Dataset", ...record keys in
    record order}`.
  - Nested `@type` follows R-04. `@type` is the first key of each nested object.
  - It is serialised like `output_json`: `ensure_ascii=False`, `indent=2`, a trailing newline.
  - It warns on stderr about nested keys that have no term (R-07). `convert` validates before
    writing, as it does for every format.
- **Canonical reader (rule J1).** There is no processor here either. The document is parsed with
  the existing duplicate-key-rejecting JSON loader. If:
  - the root `@context` is a bundled context, embedded or referenced by a known URL;
  - the only `@` keys are the root `@context` and `@type` on any object;
  - every `@type` value is a string or an array of strings;

  then `@context` and `@type` are removed (FR-009), and the rest goes through the same path as
  `input_json`. Schema validation then applies as for JSON.
- **General reader (rules J3 to J6)**, for any other JSON-LD form: expanded, compacted with
  another context, or `@graph` with one node.
  - It needs the optional extra `fair-bioheaders[jsonld]` = `pyld>=3.3,<4`, on Python 3.10 or
    later. PyLD 3 requires Python 3.10 (PyLD 3.3.0 README: "Python (3.10 or later)") and uses
    `X | Y` annotations at import time.
  - PyLD is imported lazily. Without it, the general path fails with `FHR: reading this JSON-LD
    form needs the jsonld extra: pip install "fair-bioheaders[jsonld]"`.
  - Expansion uses a **document loader that serves only bundled contexts** and raises "loading
    document failed" for every other URL. No network is used.
  - Dropped terms are collected with PyLD's `on_property_dropped` callback (prototype: it
    reported `keywords` and the nested `checksum`).
  - The expanded tree is mapped back to FHR keys by a small, deterministic **expanded-form
    mapper**. It uses the reverse of the mapping derived from the bundled context, and walks the
    scopes root, taxon, author, accessionID, vitalStats and software. **No JSON-LD compaction is
    used.**
- **Why there is no compaction.** In the prototype, PyLD 2.0.4's compaction ignored the
  property-scoped contexts and produced `taxon.genome` instead of `taxon.name`. PyLD 3.3.0
  compacted correctly. A mapper over expanded form does not depend on term selection, `@set`
  shaping or compaction bugs, and it makes unknown IRIs trivial to detect.

**Rationale**:
- MVP writing and canonical reading need nothing beyond the standard library, so the toolkit's
  runtime dependencies are unchanged (toolkit constitution V), and both work on Python 3.9.
- Only reading arbitrary third-party JSON-LD (US3, P2) needs a processor, and that is an
  explicit opt-in extra.
- The offline loader satisfies FR-005 and spec#44 ("an untrusted header URL must not trigger
  arbitrary automatic fetches").

**Alternatives considered**:
- *`pyld` as a hard dependency.* Rejected: it adds `lxml`, `cachetools` and `frozendict` to every
  install, and it drops Python 3.9.
- *PyLD 2.0.4 on Python 3.9.* Rejected: it has the compaction bug above and no
  `on_property_dropped`. Its expansion matched 3.3.0 in the prototype, but the general path would
  still need a second unknown-term mechanism.
- *rdflib's JSON-LD parser.* Rejected: it parses to RDF triples, which loses array order and the
  JSON number types. It is also a larger dependency.
- *A home-grown JSON-LD expander.* Rejected: an expander is far more than "small", and it would
  be a second implementation of a W3C algorithm.

## R-12. What "round trip" means, and the known losses (FR-004, SC-001)

**Decision**: A round trip means: an FHR record, converted to JSON-LD by the toolkit and read
back, equals the original as a JSON value. Objects are compared ignoring key order. Arrays are
compared in order. Strings, integers, floats and booleans must match in both value and JSON type,
so `1` is not `1.0`.

- **Through the canonical path (J1)** this holds for **every** valid FHR record, including
  open-object extras and empty arrays. The prototype matched 34 of 34 records: both examples, the
  YAML example and all 30 valid-vector headers, since stripping only reverses what the writer
  adds. SC-001 is tested this way.
- **Through the general path** (expanded form or another compaction) it holds for records whose
  keys all have terms. In the prototype that was 32 of 34: the two `*-nested-checksum` vectors
  lose `taxon.checksum`, which is reported (R-07). It also held for a document compacted against
  `{"@vocab": "http://schema.org/"}` (US3 "compacted differently").
- **Linked-data (RDF) losses**, documented in `docs/JSONLD.md` and the mapping table's `loss`
  fields:
  - `@set` arrays lose their order (authors, `identifier`);
  - empty `@set` arrays produce no triples;
  - JSON `1.0` becomes `"1"^^xsd:integer`;
  - open-object extra keys are dropped.

  RDF is not a round-trip path.

**Rationale**: Toolkit constitution IV says values *and types* are kept. The canonical path is
exact by construction. The general path is exact for everything FHR defines.

**Alternatives considered**:
- *Promising an RDF round trip.* Rejected: JSON-LD's RDF conversion loses array order and the
  integral-float distinction by design.

## R-13. Reading rules and conformance vectors (constitution III)

**Decision**: `docs/JSONLD.md` states the reading rules J1 to J7. Each has conformance vectors in
`conformance/` with `"format": "jsonld"`, and the manifest gains `"jsonldSpecification":
"docs/JSONLD.md"` and rule summaries. The rules:

- **J1. Canonical form.** A root `@context` that is a published FHR context (embedded) or a known
  FHR context URL, plus `@type` on any object, and no other keyword: both are set aside, and the
  rest is FHR JSON.
- **J2.** Duplicate object keys are invalid, as in JSON.
- **J3.** Any other form is interpreted by JSON-LD 1.1 expansion using bundled contexts only. A
  context that is not bundled, whether remote or unknown, is invalid. Nothing is fetched.
- **J4.** Exactly one top-level node, or one inside `@graph`. Every property must map to an FHR
  field in its scope. Unmapped or dropped terms are reported, and the document is invalid
  (the toolkit's `--ignore-unknown-terms` turns them into warnings).
- **J5.** Values:
  - an IRI-valued field accepts `{"@id"}` or a string;
  - `dateCreated` accepts `xsd:date` or an untyped string;
  - any other datatype is invalid;
  - more than one value for a single-valued field is invalid;
  - arrays keep document order;
  - `commandLineOption` comes from `@list`;
  - an `assemblySoftware` whose only value is a string is the legacy string;
  - a node referenced only by `@id` (flattened form) is invalid in release 1.
- **J6.** The result must validate against `fhr.json`.
- **J7. Writing.** The writer's output, defined byte for byte in
  [contracts/cli.md](contracts/cli.md), equals `examples/*.fhr.jsonld`.

The vectors (generated by `scripts/make_conformance.py`):
- **Valid**:
  - canonical, embedded;
  - canonical by URL reference;
  - keys reordered;
  - expanded;
  - compacted against schema.org `@vocab`;
  - `@graph` with one node;
  - legacy software string;
  - open-object extra key under J1.
- **Invalid**:
  - unknown term;
  - remote context;
  - two top-level nodes;
  - two values for `genome`;
  - flattened;
  - typed `dateCreated` as `xsd:dateTime`;
  - duplicate key;
  - canonical but missing `checksum` (J6);
  - `@id` at the root under J1 (not canonical; through the general path it is unmapped and
    invalid).

`scripts/check_conformance.py` runs `fhr-convert in.jsonld out.json`, as it does for microdata.
It gains a `--skip-format jsonld` option, so the CI job that pins the older converter
(`fhr==0.3.3`) keeps passing until a release with JSON-LD exists.

**Rationale**: Constitution III says "every parsing rule needs a conformance example". The
microdata rules M1 to M4 are the precedent.

**Alternatives considered**:
- *Toolkit-only tests.* Rejected: other implementations, such as the website builder, need
  implementation-neutral vectors.

## R-14. Testing strategy

**Decision**:
- **JSON-LD processor for tests.** PyLD, which is BSD-3-Clause (<https://github.com/digitalbazaar/pyld>),
  as a **dev-only** dependency:
  - FAIR-bioHeaders-Specification: `requirements-jsonld.txt` with `PyLD==3.3.0`, installed by CI next to
    `requirements-linkml.txt`. The tests that need it are skipped with a clear message when it is
    absent.
  - Toolkit: the `jsonld` extra plus the dev group, with Python ≥ 3.10 markers. On Python 3.9 the
    general-path tests are skipped (`pytest.importorskip`), and the writer and canonical-path
    tests still run.
- **Round-trip tests** (SC-001) over `examples/*.fhr.json`, the YAML example and every
  `metadata` header of `conformance/valid`:
  - through the canonical path (exact equality as in R-12);
  - through PyLD expansion and the expanded-form mapper (exact for records without unmapped
    nested keys).

  Toolkit: the same, plus every CLI conversion pair, for example `json → jsonld → yaml → jsonld`,
  with byte-identical `jsonld` output.
- **Expansion checks** (SC-003). The expanded predicates and `@type` IRIs of every example and
  vector must lie in `http://schema.org/`, `https://w3id.org/fair-bioheaders/terms#` or
  `rdf:` (`type`, `first`, `rest`, `nil`), and datatypes in `xsd:`. Every `fhr:` IRI used must be
  defined in `jsonld/terms.ttl` with a label and a description (FR-002).
- **schema.org validation offline.** `validator.schema.org` has no offline mode. Instead:
  - `scripts/make_jsonld.py --schemaorg-subset` extracts, from the pinned release file
    `https://schema.org/version/30.1/schemaorg-current-https.jsonld` (SHA-256 recorded), the
    terms the context uses, with `domainIncludes`, `rangeIncludes`, `subClassOf` and pending
    status;
  - it commits them as `tests/fixtures/schemaorg-v30.1-subset.json`, with attribution;
  - a test asserts that every `sdo:` term exists, that its pending status matches the mapping
    table, and that every property is used only on a node type in its domain, including
    superclasses.

  This would have caught `sdo:relatedLink` on Dataset. A manual check with
  `https://validator.schema.org/` on an HTML page that embeds `examples/example.fhr.jsonld`
  (quickstart V5) is recorded in the PR; it is not a CI gate.
- **Mapping-table tests** (SC-002):
  - the table validates against `mappings/mapping-table.schema.json`;
  - the set of paths equals the set of all property paths in `fhr.json`, including nested ones
    (45);
  - every entry has a DCMI value or `none` plus a kind;
  - `conditional` entries have a `condition` and `lossy` entries a `loss`;
  - JSON-LD terms equal the IRIs derived from LinkML;
  - DCMI terms exist in a pinned DCMI term list, committed as
    `tests/fixtures/dcmi-terms-2020-01-20.txt`.
- **Byte-identity tests**:
  - toolkit `bioheaders/fhr.context.jsonld` equals the specification's `jsonld/fhr.context.jsonld`
    (`check_release.py` extended);
  - the JSON-LD examples are identical in both repositories (existing `check_release.py` loop).
- **No network**. All tests use the bundled-only document loader, and a test asserts that loading
  any other URL raises.

**Rationale**: These tests cover SC-001, SC-002 and SC-003 automatically, and SC-004 is the
maintainer's confirmation. Every test runs offline.

**Alternatives considered**:
- *Calling validator.schema.org in CI.* Rejected: it needs the network, it is not a
  documented API, and it is not deterministic.
- *Committing the whole 1.5 MB schema.org release file.* Rejected: it is large, and only about
  30 terms are needed.

## R-15. Machine-readable mapping table for #56

**Decision**: A new YAML file, `mappings/fhr-jsonld-dcmi.yml`, validated by
`mappings/mapping-table.schema.json` ([contracts/mapping-table.schema.json](contracts/mapping-table.schema.json)).
The header block follows `fhr_mappings.yml`'s conventions: `id`, `source_schema`, plus pinned
`targets` with version and reference URL. There is one entry per FHR path:

```yaml
- path: reuseConditions
  jsonld: {term: "http://schema.org/license", status: core, kind: conditional,
           condition: "the value identifies a licence (SPDX id or licence URL)"}
  dcmi:
    - {term: "http://purl.org/dc/terms/rights", kind: broader}
    - {term: "http://purl.org/dc/terms/license", kind: conditional,
       condition: "the value identifies a licence"}
  notes: "Preserve text; do not infer a standard licence from prose (#56)."
```

- `dcmi` is a list, possibly `[{term: none, kind: unsupported, reason: ...}]`, so #56 can record
  several DCMI options without a schema change.
- An optional `subject: record` marks statements about the metadata record (rows 1 and 9), as
  #56's resource model requires.
- An SSSOM TSV export is a possible later step: each kind maps to a SKOS predicate (R-02).

**Rationale**:
- #56 asks for crosswalks with "field path, target term/path, cardinality, conditions,
  transformation, provenance, information loss, and examples" and for reuse of the current
  conventions. YAML with a JSON Schema matches `fhr_mappings.yml` and the rest of the repository.
- A list of DCMI targets per path covers the conditional, multi-target cases.

**Alternatives considered**:
- *Extending `fhr_mappings.yml`.* Rejected: it is a projection specification
  (`class_derivations`/`slot_derivations` with expressions) executed by `project_mixs.py`. A
  crosswalk of term equivalences is a different kind of document, and mixing them would break that
  script's assumptions.
- *SSSOM as the primary format.* Rejected for release 1. SSSOM needs CURIE subjects for nested
  JSON paths, and it has no native `conditional`/`lossy`. It remains an export target.

## R-16. A record that cites a raw-main or a versioned schema URL (spec#44 edge case)

**Decision**: JSON-LD changes nothing about the schema URL:
- `schema` is copied as the `sdo:schemaVersion` IRI, whatever URL the record cites;
- validation after reading follows the toolkit's existing policy for the cited version
  (spec#44);
- the context is independent of the schema URL;
- a conformance vector and a round-trip test use a record citing the raw-main URL and one citing
  `https://w3id.org/fair-bioheaders/fhr/v0.4.0`.

**Rationale**: The spec Assumptions say the schema-authority decisions apply to the cited URL.
This feature must not create a third policy.

**Alternatives considered**:
- *Rewriting raw-main to a versioned URL in the JSON-LD output.* Rejected: it changes a user
  value (FR-004), and it pre-empts spec#44.

## R-18. Maintainer decisions as implemented (MVP, 2026-10-10)

The plan's maintainer decisions change four earlier choices; tasks T046 and T048 implement them.

- **Author typing** (decision 4). ORCID → `sdo:Person`, ROR → `sdo:Organization`, otherwise
  `fhr:Agent`. LinkML: `jsonld_type_if_orcid` and `jsonld_type_if_ror` on `Author`. The author
  scope gains the type term `Organization`.
- **`documentation`** (decision 3). A context cannot choose a predicate by value, so the writer
  writes an absolute URL under a different key, `subjectOf` (`sdo:subjectOf`, IRI-coerced, from
  the LinkML annotation `jsonld_slot_uri_if_url`), and the canonical reader maps it back. This is
  the one place where the JSON-LD key differs from the FHR key (FR-007), and the round trip stays
  exact.
- **Bioschemas** (decision 2). An export context outside the record supplies `id`, `url` and
  `keywords`; the root scope gains the output-only terms `keywords`, `url` and `conformsTo`
  (`dct:conformsTo`). `dct:conformsTo` is emitted only when every Dataset minimum property is
  present. Two corrections to the task text: the minimum list of Dataset 1.0-RELEASE includes
  `@id`, so the export context also takes the dataset `id` (written as the root `@id`); and
  Dataset 1.1 is still `1.1-DRAFT` on the profile index (checked 2026-10-10), so the claim is
  `https://bioschemas.org/profiles/Dataset/1.0-RELEASE`, not 1.1-RELEASE. The canonical reader
  accepts a root `@id` and sets the export terms aside with a warning, since they are not FHR
  fields.
- **Context URLs** (decision 1). Not implemented in the MVP (T044, T045). The toolkit bundles
  the context of `main` only and recognises only the raw-main URL until a release contains the
  file.
