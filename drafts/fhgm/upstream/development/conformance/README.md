# Draft FHGM conformance vectors and model-level checks

Status: draft-stage conformance for the [reviewed native model
contract](../model/README.md) under shared
[#204](https://github.com/FAIR-bioHeaders/FAIR-bioHeaders-Specification/issues/204).
FHGM has no released contract, no `schemaVersion`, no schema URL and no
`schemas/versions.json` entry, and selection rule V7 keeps it that way until the
shared publication PR lands. Nothing in this directory publishes, adopts or
claims toolkit support; `check_draft.py`'s matrix and this suite are
[the draft's own checks](../model/README.md#running-the-draft-checker), now wired
into CI.

## Why a separate suite

An FHGM model record lives under the FHGFF3 header's `x-fhgm-models` extension
key, whose content the released base schema does not constrain. Model-level
predicates require a separate checker, including feature target resolution and
bounded revision context. The current suite has 92 vectors (24 valid,
68 invalid); 63 invalid cases per base lane earn a model rejection while the
base header and checksum pass. Boundary refusals and unavailable evidence do
not count as model rejections. [D4–D6](DECISIONS-2026-11-19.md) defines that
separation and the actual evidence counts.

## Layout

- `manifest.json` — the rule ids, the open-scope list and the expected outcome of
  every vector, including the prior snapshots each pointer check is handed. The
  sealed lane runs all 92 vector entries, with the FHGFF3 1.1 (v0.5.0) bytes as
  its base layer.
- `base_matrix.json` — the FHGFF3 1.2 matrix lane: for every sealed vector, the
  identity-rewritten twin's sealed digest and the layers observed against the
  v0.6.0 base, with an explicit agreement flag per vector (maintainer dual-base
  decision 2026-11-15; see "Base matrix" below).
- `../model/base-schemas.json` — the registry the checker reads: which released
  FHGFF3 bytes are admissible as `--base-schema` candidates and how a carrier's
  declared `schemaVersion` selects among them.
- `vectors/valid/`, `vectors/invalid/` — byte-exact GFF3 files generated by
  `make_vectors.py`. Never open and re-save them.
- `make_vectors.py` — deterministic generator, reusing the
  [revision pilot](../examples/revision/README.md) render helpers, the same
  synthetic assembly and the same one-record SeqCol collection as the v0.1
  fixture set.
- `make_dmel_vectors.py` — companion generator for the promoted real-data batch:
  each emitted file is one committed [dmel4](../examples/dmel4/README.md)
  fixture header with exactly one documented producer-error mutation, rendered
  canonical-line with a fresh computed checksum over the fixture's own verbatim
  RefSeq feature rows. Draft promotion packet:
  [PROMOTION-2026-11-15.md](PROMOTION-2026-11-15.md).
- `run_conformance.py` — the independent runner. It imports nothing from
  `check_draft.py` or from the generators, recomputes every checksum with
  `hashlib`, derives the 1.2 twins from the sealed bytes by the same standard
  library, and reads outcomes only from a run of
  [`validate_fhgm.py`](../model/validate_fhgm.py).
- `provenance.json` — repository, ref, commit, path, SHA-256 and retrieval date
  for the pinned base schema, plus the digests of the contract and generator
  bytes these vectors were observed against.

`.gitattributes` keeps the bytes in this tree free of line-ending conversion.

## Reuse, not a second machinery

The vectors reuse the overlay and snapshot machinery merged in
[`bc4d45d`](https://github.com/FAIR-bioHeaders/FHGM-Specification/commit/bc4d45ddb058592e10ca030ca67773c9ec26fa45)
(draft transport overlay and snapshot validation) and
[`8b0ca00`](https://github.com/FAIR-bioHeaders/FHGM-Specification/commit/8b0ca0055b84d69bc24e5daf4ad1950e91d11d0e)
(native record contract, checker and v0.1 fixture set): the same
`fhgm-draft.schema.json`, the same `fhgm-model.schema.json`, the same checker,
the same `render`/`synthetic_reference`/`feature_payload` helpers. The census
retains all earlier vectors and adds the selected Round 14 cases. Nothing
here re-implements a reader, a checksum or a validator.

## Layers

Each vector records four separate outcomes, as FHGM #9 requires. They are
reported separately and never collapsed into one "valid" boolean:

| Layer | What ran | Authority |
| --- | --- | --- |
| `base` | the released `fhgff3.json` schema alone, over the header as the toolkit's strict reader parses it | the shared specification's v0.5.0 bytes for the sealed lane (`provenance.json` `baseSchema`), v0.6.0 for the matrix twins (`matrixBaseSchema`); separately, the checker selects the release each file cites and prints it |
| `checksum` | `verify` or `stale`, recomputed with `hashlib` over every byte except the root checksum line | `docs/FORMAT.md` R1–R4 |
| `gff3` | `gff3-validate --no-header`, when that separate tool is installed | gff3-validator, not this contract |
| `model` | `validate_fhgm.py`: transport overlay, native record contract, rules K3–K6 and the pointer verdict | the reviewed draft contract |

The external GFF3 executor is separate from the model predicate. The checker
must read a complete trustworthy local inventory for K4; skipping the external
tool never removes that requirement. A full model pass also requires the
relevant supplied snapshots' inventories for K6. One new bare-Parent case earns
both an independent GFF3 syntax rejection and a model-scope rejection; all
other cases retain their separately recorded GFF3 outcomes.

Manifest `ruleRequirements` declares inputs for every K rule, not only the
vector's focus labels. `layers.model` preserves the historical combined
checker-process outcome; `evidenceExpectation.model` and actual JSON receipts
state earned model evidence. Missing/untrustworthy inputs stay not-run/refused,
known complete empty inventories reject K4, and no partial pass counts as a
complete model pass. See [the selected decisions](DECISIONS-2026-11-19.md);
the earlier layer proposal is retained as historical context.

## Rules

`K1`–`K6` and `B1` are drafted in this repository and are **not** registered in
the shared manifest, whose `R1`–`R15`, `M`, `J`, `P`, `G` and `V` namespaces keep
their meanings. Vectors may cite those shared ids as well; where they do, the
shared text stays authoritative and this manifest only cites it.

| Id | Rule | Source |
| --- | --- | --- |
| `K1` | Transport: a released FHGFF3 identity — v0.5.0/1.1 or v0.6.0/1.2 per the dual-base decision of 2026-11-15 — plus a non-empty `x-fhgm-models` array; a 1.0 file cannot carry the extension at all | [model README](../model/README.md#transport-fhgff3-embedded-records-normative-draft-wording), FORMAT.md R15 |
| `K2` | Record shape: required `modelId`, `modelVersion`, `featureId`, `reference`; closed nested objects; opaque values are non-empty, trimmed text without control, zero-width or bidirectional formatting characters; link fields take a FORMAT.md R14 scheme and must be valid URIs | [`fhgm-model.schema.json`](../model/fhgm-model.schema.json) |
| `K3` | `modelId` unique within one snapshot, compared after NFC normalisation and before any per-record rule; a duplicate is the named outcome `ambiguous` and rejects that snapshot (checker rule 1, deviation D4) | [model README](../model/README.md#model-level-constraints-the-base-schema-cannot-enforce) |
| `K4` | `featureId` resolves, percent-decoded, to exactly one local root gene row: type `gene` or `SO:0000704`, no `Parent` (checker rule 2) | as above |
| `K5` | A record `reference` shares at least one comparable form with the file genome link and never contradicts it (checker rule 3, deviation D1) | as above |
| `K6` | A predecessor pointer resolves against explicitly supplied snapshots only: it names its own `modelId` (D2), versions differ, assembly and record links match, and a recorded successor in the supplied set is not skipped (D3) | as above |
| `B1` | Boundary: a file must already satisfy the released base schema and its exact-byte checksum before any FHGM verdict exists, so a `B1` rejection is not evidence of a model-level gap | [model README](../model/README.md#transport-fhgff3-embedded-records-normative-draft-wording) |
| `R3`, `R15` | Cited shared FORMAT.md rules: checksum coverage of the record bytes, and the extension-field floor | `docs/FORMAT.md` in the shared specification |

Pointer resolution depends on the history the reviewer hands over, so a vector
may declare `context.predecessors`. Two vectors can therefore share one file and
differ only in what was supplied — that pair is how deviation D3's bound is
pinned (`gap-skip-with-recorded-successor-supplied` against
`gap-pointer-without-recorded-successor`).

## Mutation check

Every guard in `validate_fhgm.py` must be noticed by at least one vector, so
that deleting or weakening it turns the suite red. On 2026-11-18 each of the
following was applied to a copy of the checker, and the copy was run over all
vectors listed in `manifest.json` (with their recorded histories) and over the
checker-function tests
in `tests/test_fhgm_conformance.py` (`CheckerGuards`, pointed at the copy via
`FHGM_CHECKER`). Every mutation was caught:

| Mutation | Caught by |
| --- | --- |
| K4 accepts any row type | `feature-target-root-transcript-row` |
| K4 accepts several rows per ID | `feature-target-duplicate-rows` |
| K4 compares raw instead of decoded IDs | `percent-decoded-feature-target`, `feature-id-names-percent-encoding` |
| K4 also matches the raw ID | `feature-id-names-percent-encoding` |
| K4 ignores `Parent` on the target | `feature-target-gene-with-parent` |
| K5 drops the comparable-form half | `reference-forms-not-comparable`, `dmel-reference-not-comparable` |
| K6 drops the recorded-successor check | `gap-skip-with-recorded-successor-supplied` |
| K6 drops the assembly-link match | `pointer-assembly-link-differs` |
| K6 drops the record-reference match | `pointer-record-reference-differs` |
| K6 resolves when the snapshot lacks the model | `pointer-snapshot-lacks-model` |
| K6 drops the current-file guard | `CheckerGuards` only |
| K2 without the URI format checker | `record-evidence-uri-not-a-uri` |
| K2 allows user information without a host | `record-evidence-uri-user-info-without-host`, `record-methods-protocol-ftp-user-info-without-host`, `record-software-uri-empty-user-info-and-host`; accepted control `record-links-user-info-before-host` |
| K3 without NFC normalisation | `model-ids-equal-under-nfc` |
| K3 run after the per-record checks | `duplicate-model-id-reported-before-record-checks` |

The current-file guard is the one no byte vector can reach: a pointer cannot
honestly name the checksum of the file that carries it, because the pointer text
is inside the bytes that checksum covers. It is exercised on the checker's
`resolve_predecessor` function directly, with a control that the same pointer
into a different supplied snapshot resolves.

## What the feature layer does not catch

`layers.gff3` is gff3-validator 0.1.0 run with `--no-header`. It accepts every
vector here, and it also accepts gene models that are structurally broken.
Measured on 2026-11-18 with gff3-validator 0.1.0 and the checker on this
branch; every file below has an otherwise valid FHGM record targeting the gene:

| Feature-layer defect | gff3-validator 0.1.0 | FHGM checker |
| --- | --- | --- |
| CDS outside every exon of its transcript | accepts | passes |
| mRNA and exon on the opposite strand from their gene | accepts | passes |
| Child feature outside its parent's coordinates | accepts | passes |
| `Parent` on a different seqid from the child | accepts | passes |
| The targeted gene row has an mRNA `Parent` | accepts | rejects (K4, root row) |
| Target typed `ncRNA_gene` or `pseudogene` | accepts | rejects (K4, type) |

So a passing run across all four layers says nothing about whether the targeted
gene model is internally coherent. An exon with several parents
(`Parent=m1,m2`, shared by isoforms) is ordinary GFF3 and is accepted by both,
correctly. The selected D5 decision keeps graph and biological structure with
gff3-validator and limits initial FHGM targets to one root `gene` or
`SO:0000704` row. The four listed structural gaps remain visible; no graph
implementation or closure in gff3-validator is claimed here.

## Base matrix: both released FHGFF3 bases

Decision (maintainer, 2026-11-15): FHGM must be describable on **both** released
FHGFF3 bases. The released toolkit (`fair-bioheaders` 0.11.0) writes
1.2 headers today, while the sealed vectors and fixtures carry 1.1 bytes; before
this decision a 1.2 carrier with `x-fhgm-models` failed the draft's own harness
at `$.schemaVersion: '1.2' is not one of ['1.0', '1.1']`.

Implementation — base **selection**, not base substitution:

- `../model/base-schemas.json` registers the two releases by exact-byte digest,
  each resolved from its tag to its commit; the checker refuses any other bytes.
- The carrier's cited `schema` URL selects the release that validates it: the
  registry lists, per release, the w3id URL with and without the trailing slash
  and the raw tag URL under both repository names (FAIR-bioHeaders-Specification
  and the FHR-Specification alias). `schemaVersion` plays no part in the
  selection; the cited release's own bytes judge it. A citation no registered
  release answers to (a superseded release such as v0.4.0, or raw main), a
  missing citation, and a citation whose release bytes were not supplied are
  all refused with a selection error, never evaluated against bytes the carrier
  never cited. The selection is printed for every loaded file. (Until
  2026-11-18 the checker selected by `schemaVersion` and fell back to the
  oldest supplied base; that fallback is gone.)
- The transport overlay admits exactly two closed identity branches (the v0.5.0
  URI set with `1.1`; the v0.6.0 URI set with `1.2` or `1.1`, since the v0.6.0
  release accepts `1.1` records), so a citation and a version that contradict
  each other, such as a v0.5.0 citation stating `1.2`, are rejected.
- The original 31 `manifest.json` vector entries — bytes, layers, reasons,
  contexts — are **unchanged**; the 12 promoted entries are also evaluated in
  both lanes. The sealed lane's base layer is the v0.5.0 bytes, and its rule
  text was updated only where K1's identity wording became false. The
  base-selection change of 2026-11-18 moved one reason substring
  (`transport-1-0-extension`, now refused at selection) and added four vectors.
- `base_matrix.json` is the added lane. A twin replaces exactly two header
  lines of its vector (a v0.5.0 `#~schema` citation moves to the v0.6.0 w3id
  citation and any other citation is kept; `#~schemaVersion` moves to `1.2`;
  quoting style preserved) and the `#~checksum` line follows:
  recomputed for `verify` vectors, kept stale for the `stale` one. The 1.0
  vector gets no rewrite — its stated identity IS the defect — so it is
  evaluated as committed under the 1.2 base. Predecessors stay the committed
  files, making the lane a mixed-identity chain test as well. Both lanes hand
  the checker both base files, so a 1.1 predecessor of a 1.2 twin is judged by
  the v0.5.0 bytes it cites; before 2026-11-18 the matrix lane passed only the
  v0.6.0 bytes and the predecessor was judged by them.

Measured result (re-sealed 2026-11-18 by `--seal-matrix`): **62 twins, 0 verdict
changes** — every twin reproduces its sealed vector's four layers and reason
substring under the v0.6.0 bytes, and the gap claim holds identically on both
bases (42/45 rejections gap-proof). No contract finding came out of the
comparison; the reason is visible in the release diff itself: between v0.5.0
and v0.6.0 `fhgff3.json` the schemaVersion enum gains `1.2`,
`Completeness.lineageDataset` gains dotted BUSCO dataset versions for carriers
declaring `1.2`, two version-gated if/then clauses keep the old pattern for
`1.0`/`1.1` carriers, and description text moved. No FHGM vector or fixture
byte carries a `completeness` object, so none of the real delta can move an
FHGM verdict; the matrix measures that rather than assuming it.

## Running the suite

From the repository root, with `fair-bioheaders` and `jsonschema` installed (the
checker reuses the toolkit's header reader and checksum implementation):

```sh
git -C /path/to/FAIR-bioHeaders-Specification show v0.5.0:fhgff3.json > /tmp/fhgff3-v0.5.0.json
git -C /path/to/FAIR-bioHeaders-Specification show v0.6.0:fhgff3.json > /tmp/fhgff3-v0.6.0.json
python3 development/conformance/run_conformance.py \
  --base-schema /tmp/fhgff3-v0.5.0.json --base-schema /tmp/fhgff3-v0.6.0.json
```

Both base files are required for any run that reaches the model layer: vectors
and their predecessors cite either release, and the checker refuses a citation
whose bytes were not supplied. Add `--matrix` to run the 1.2 twin lane against
`base_matrix.json` as well; CI runs both lanes on every pull request. Add `--gff3-validate /path/to/gff3-validate` to include the feature
lane, and `--verbose` to list every vector of every lane, not just failures. `--offline` runs the byte,
digest and checksum layer with the standard library alone and reports the model
lanes as skipped, so a checkout can always be integrity-checked. Exit status is
0 on a full match, 1 on a mismatch and 2 when the suite itself cannot run.

The runner verifies, in order: that `provenance.json` agrees with the
`base-schemas.json` registry the checker loads and with the contract and
generator bytes in this tree, and — with `--matrix` or offline whenever
`base_matrix.json` exists — that every twin re-derives byte-for-byte from its
sealed vector and that each matrix entry agrees with its manifest counterpart;
that every generated vector is reproduced byte-for-byte by its generator; that
each vector's size, SHA-256 and stated checksum line match the manifest; that the
recomputed SHA-512/256 agrees with the toolkit's; and only then the recorded
layer outcomes and reason substrings. A contract or generator edit therefore
surfaces as a provenance failure until `provenance.json` is re-recorded and
`--seal` re-records the vector digests — `--seal` refuses to write when any vector
mismatches, so it can never paper over a changed expectation.

## Relationship to the shared conformance suite

The absorption decision is open and belongs to the publication PR: extend the
shared `conformance/manifest.json` with a checker-vector lane, or keep a separate
FHGM suite in the shared repository. This directory is the seed either way — it
is manifest-shaped (`manifestVersion`, `rules`, `vectors`, `retired`, kebab-case
ids, `valid`/`invalid` expectations with one broken rule per invalid vector), and
it stays in this repository while the contract is unreleased, because publishing
vectors beside a released suite would put a draft into a release form that V7
forbids. Absorbing it later needs a decision on the `K`/`B` id namespace and on how
a vector carries a `context.predecessors` snapshot, neither of which the shared
manifest has a shape for today.

## What this suite does not establish

- It does not certify biological correctness, orthology or feature quality. The
  feature layer belongs to gff3-validator, reference matching to its own inputs.
- It does not assert curator acceptance of any revision; resolution and acceptance
  are separate (O8).
- It adds no INSDC coverage to any released contract — see
  [the coverage supplement](../INSDC-COVERAGE.md).
- It is not a support claim. No toolkit, builder or website feature is implied by
  a passing run here; [Tools #135](https://github.com/FAIR-bioHeaders/FAIR-bioHeaders-Tools/issues/135)
  stays gated on publication.
- It does not include a real annotated-genome pilot. See the next paragraph.

## What is missing: real annotated-source vectors

Every vector except `s6k-derived-record-fixture` is synthetic, and that one
fixture derives from a deposit that is a single-locus ortholog model. #206
pilot data cannot yet extend this suite: the maintainer's named dataset,
*Prosapia bicincta* `GCA_036971475.1`, is a genome-only assembly with no
annotation release — its feature count reports zero unique IDs and it publishes
no `.faa`, `.gff3` or CDS files. There is consequently no source data from which
to derive an FHGM gene model (or an FHGFF3 annotation) for that organism, and no
gene model has been fabricated to fill the gap. FHGM fixtures with a companion
annotation release remain an open item of
[#206](https://github.com/FAIR-bioHeaders/FAIR-bioHeaders-Specification/issues/206).

The promotion PR stays a draft until a second reader has reviewed the

The dual-base decision adds
`base_matrix.json`, the `base-schemas.json` registry and the runner's

The contract-only acceptance matrix in `development/model/check_draft.py` also
